Motivation The Kafka producer's current memory allocation strategy reserves at least the full "batch.size" of pool memory for each partition that becomes active (starts a batch), regardless of how much data the batch ultimately holds before it is sent. Pool reservation therefore scales with the active-partition count, homogeneously for all active partitions. Under the default partitioning logic (partitioner.class unset and sticky behaviour introduced by KIP-480/KIP-794), this is not particularly problematic: records without keys stay on one partition per topic at a time, switching after at least batch.size bytes have been produced to the partition. A pure keyless workload's memory footprint stays bounded regardless of the number of partitions.

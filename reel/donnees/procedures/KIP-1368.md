Motivation The Apache Kafka clients are often wrapped by frameworks such as Spring. Kafka does this itself in Kafka Streams and Kafka Connect. There is no architected way of identifying clients running within such frameworks which can hinder problem determination. When diagnosing an issue from the client logs, the application code is not directly calling the Kafka client. This means there's a mismatch between what the application developer wrote and how the Kafka client is being used. Behaviors such as retries or transactions can be implemented in the framework rather than the application. Having the information about whether a framework is being used can illuminate why the application is appearing to behave in a particular way. Proposed Changes Three client configurations are added which can be set by frameworks embedding Kafka clients (producer, consumer and admin).

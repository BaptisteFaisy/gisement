Motivation Kafka now uses "features" to declare the capabilities it supports. Features are versioned to evolve over time. The initial versions are set when formatting and can be updated at runtime via the UpdateFeatures API. Brokers support a range of versions for each feature, and at a single time there is a finalized version that indicates the current version in use. The finalized version for each feature is a cluster-wide state: when upgrading or downgrading a feature, all brokers have to support it. Each broker reports the ranges it supports as well as the finalized versions. This is exposed via the Admin API. Another version that is less visible is the "default" version of each feature for a specificmetadata.version. It is also a cluster-wide state. This is what is picked when formatting a node, or when finalizing an upgrade viabin/kafka-features.sh upgradewith the--release-versionflag. The default version is also by convention what is used in documentation, i.e. "feature X is at version Y in Kafka …

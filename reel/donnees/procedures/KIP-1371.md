## Objet

Status Current state: Under Discussion Discussion thread:[DISCUSS] KIP-1371: Explicit Wait Conditions for Consumer Request Managers JIRA:KAFKA-20995 Release: TBD Summary The async consumer has repeatedly entered busy loops when a timer reaches zero while another state blocks the related work. The current numeric wait says when to poll again, but it cannot say whether time can make the work eligible or another event must occur first. Existing fixes replace the zero with another duration, which can make correctness depend on that duration's configuration. This KIP introduces the internalManagerPollConditiontype withready(),after(...), andidle(). Each request-managerpoll()returns its outgoing requests and the condition for the next manager pass. The same manager decision can govern request admission and network scheduling. The network thread combines all manager conditions and applies the existing network-poll bounds. Public APIs, protocols, and thread topology remain unchanged. The internal per-managerRequestManager.maximumTimeToWait(long)method becomesapplicationPollCondition(long); the application-facingApplicationEventHandler.maximumTimeToWait()path remains unchanged.

Motivation The ZooKeeper-to-KRaft migration is designed so that a cluster can linger in thedual-write phaseand roll back to ZooKeeper mode if an operator discovers a problem before the migration is finalized. In production environments, at any point in time, hardware failures may happen, some of which are cause for replacing nodes, such as failing disks. Kafka fully supports node replacements out of the box. These two aspects (node replacements/provisioning and KRaft migration rollback) are documented as orthogonal concepts. However, it has been observed in production systems that node replacements during a KRaft migration, when following the documented procedures, breaks the ability to roll back. This is not documented, and as both mechanisms are important tooling for operators to keep clusters available, it's preferable to make them work in conjunction.
